# WebUI 改善ロードマップ

## この文書の位置付け

[webui-use-cases.md](./webui-use-cases.md) で定義したあるべき使い方と、[webui-gap-analysis.md](./webui-gap-analysis.md) で洗い出したギャップ（G-01〜G-34）を、着手できる単位へ分割して順序付けたものである。

各項目は 1 Issue に相当し、Roadmap Issue 3 本と子 Issue 31 本として起票済みである。

- #169 Roadmap:WebUI の土台と画面構造を作り直す（Phase 0, 1）
- #170 Roadmap:画像管理と制作工程を WebUI で成立させる（Phase 2, 3, 6）
- #171 Roadmap:プロンプト編集と Preset 運用を仕上げる（Phase 4, 5, 7, 8）

方針は次のとおり。

- **画面を使いやすくすることを優先する。** データモデルの拡張やエンジン追加より、既にある機能を使える形で出すことを先に行う。
- **見た目のリッチさも同格で扱う。** 操作の分かりやすさと、画面としての完成度（視覚的な階層、状態の伝達、応答の手触り）は別の問題であり、両方を項目として立てる。
- **土台から積む。** 状態の永続化と共通部品は、後続すべての効果に乗るため最初に置く。

## UI リッチ化の現状

ギャップ分析は操作の設計を対象にしたため、画面としての作り込みは別途ここに記す。`apps/web/src/styles.css`（1,049 行）の実測。

- **色トークンは 8 個のみ**（`styles.css:3-10`: `--bg` / `--panel` / `--panel-border` / `--text` / `--muted` / `--accent` / `--danger` / `--ok`）。余白・角丸・影・字送りのスケールは定義されておらず、各所に直値が書かれている。
- **`transition` と `animation` の使用箇所は 0 件。** 状態が変わっても視覚的な変化の橋渡しがなく、切り替わりが唐突になる。`@keyframes` も無い。
- レイアウトは `grid-template-columns` を 20 箇所以上で個別指定。`@media` は 3 箇所（760px / 1050px / 700px）。
- ライトテーマは無く、配色はダーク固定。
- アイコンを持たず、操作はすべてテキストのボタン。候補 1 件あたり 7 個のテキストボタンが並ぶ（`CandidateGallery.tsx:435-441`）。
- ドラッグ＆ドロップは無い。画像の投入はすべて `<input type="file">`。
- トースト・スナックバーの類が無く、完了と失敗は各パネルのインライン表示に留まる。

これらを「リッチ化」項目（R-xx）として、機能項目（F-xx）と並べてフェーズへ配置する。

## Phase 0 ── 土台

後続すべての効果がここに乗る。API の変更を伴わない。

### F-01 画面状態を永続化して復元する (#138)

**対応ギャップ** G-05, G-06, G-08, G-09

選択中の Project / Scene / Shot / View / タブと、各フォームの入力を永続化し、リロード後に復元する。View 切替でアンマウントされても入力を失わない。主要な選択を URL に載せ、ブラウザの戻ると共有可能なリンクを成立させる。

**受入基準**

- リロード後、直前の Project / Scene / Shot / View / タブが復元される。
- View を切り替えて戻ったとき、各生成フォームの入力が保たれている。
- URL から Project / Scene / Shot / View を指定して開ける。
- 資産ブラウザから「この画像から派生生成」へ移動しても、生成フォームの入力が初期化されない。

### F-02 Recipe 変更時にプロンプトを保持する (#139)

**対応ギャップ** G-07

Recipe を切り替えたとき、使用者が入力済みのプロンプトを既定値で上書きしない。切り替えによって何が変わるかを示し、上書きするかを選べるようにする。

**受入基準**

- プロンプトを入力した状態で Recipe を変えても、入力が消えない。
- Recipe 既定値と現在の入力が異なる項目が分かる。

### R-01 デザイントークンを整備する (#140)

**対応ギャップ** UI リッチ化の現状（色トークン 8 個、スケール未定義）

余白・角丸・影・字送り・行間・境界のスケールを定義し、色の役割を分離する（背景の階層、面の階層、状態色、強調色）。各所の直値をトークンへ置き換える。

**受入基準**

- 余白・角丸・影・タイポグラフィのスケールが CSS 変数として定義されている。
- 既存画面の見た目が崩れていない。
- 新しい画面をトークンだけで組める。

### R-02 状態遷移に視覚的な橋渡しを入れる (#141)

**対応ギャップ** UI リッチ化の現状（`transition` / `animation` 0 件）

開閉・切替・出現・消失に遷移を入れる。生成中・待機中・読み込み中の状態を、静的なテキストではなく視覚的に伝える。`prefers-reduced-motion` を尊重する。

**受入基準**

- タブ切替、モーダル開閉、一覧の更新に遷移がある。
- 読み込み中の領域が、空白ではなくプレースホルダで示される。
- 動きを減らす設定が有効なとき、遷移が無効になる。

### R-03 共通 UI 部品を切り出す (#142)

**対応ギャップ** G-33、UI リッチ化の現状（アイコン無し）

ボタン・アイコンボタン・バッジ・カード・空状態・トースト・ツールチップを共通部品として定義する。主操作と副操作の視覚的な区別を付ける。テキストボタンの一部をアイコン＋ツールチップへ置き換える。

**受入基準**

- 主操作・副操作・破壊的操作が見た目で区別できる。
- アイコンボタンにツールチップとアクセシブルな名前がある。
- 候補 1 件あたりのボタンが視覚的に整理されている。

### R-04 通知とトーストを導入する (#143)

**対応ギャップ** 横断「待たせない」「取り消せる」

ジョブの完了・失敗を、作業を中断しない形で通知する。取り消し可能な操作にはトーストから取り消せる導線を付ける。

**受入基準**

- 生成の完了・失敗が、どの画面にいても通知される。
- 通知から該当の結果へ移動できる。
- 通知が作業中の入力を妨げない。

## Phase 1 ── 画面の組み替え

Phase 0 の共通部品の上に、画面構造を作り直す。

### F-03 モードA / モードB を分離する (#144)

**対応ギャップ** G-01, G-02

トップレベルを機能軸（Project / 生成 / 資産 / Workflow）からモード軸へ組み替える。モードB の画面に出すのはキャラクター・場面・Preset・実行・採否・次へに限る。エンジン名、モデル、サンプラー、ステップ、CFG、denoise、Workflow はモードA へ移す。

**受入基準**

- 起動時にどちらのモードにいるかが画面から分かる。
- モードB の画面に常時見えている操作要素が 15 個以下である（現状の生成 View は約 58 個）。
- モードB からモードA へ、現在の条件を保ったまま移動できる。
- モードA からモードB へ戻れる。

### R-05 レイアウトを可変にする (#145)

**対応ギャップ** UI リッチ化の現状（`grid-template-columns` の個別指定 20 箇所超）

ペインの幅を使用者が調整でき、不要なペインを畳める。幅の指定を共通のレイアウト部品へ集約する。

**受入基準**

- 主要画面のペイン幅を変更でき、その状態が保たれる。
- ペインを畳んで作業領域を広げられる。

### R-06 空状態と次の一手を出す (#146)

**対応ギャップ** G-31

まだ何もない画面に、何をすればよいかを示す。前提条件が満たされていない場合、何が足りないかと、それを満たす場所への導線を出す。

**受入基準**

- 一覧が空のとき、次にやることが画面に出る。
- 「Shot を選ぶと投入できます」のような条件表示から、条件を満たす操作へ移動できる。

## Phase 2 ── 画像管理

### F-04 画像ピッカーを共通化する (#147)

**対応ギャップ** G-10, G-11

3 系統（生成物 / 登録素材 / アップロード）を 1 つの選択 UI に統合し、現在 7 箇所に散っている個別実装を置き換える。複数枚が必要な箇所では役割ごとの枠を持てるようにする。API 側は指定形式が既に統一されているため、UI だけで完結する。

**受入基準**

- 画像を選ぶ操作が、画面によらず同じ手順である。
- 1 つのピッカーから生成物・登録素材・アップロードのいずれも選べる。
- 複数枚選ぶ箇所で、何枚必要で今何枚かが分かる。
- 既存 7 箇所がこの部品に置き換わっている。

### F-05 画像の取り込みに役割とキャラクターを与える (#148)

**対応ギャップ** G-12, G-14

取り込む画像に、役割（外見参照 / ポーズ / 背景 / 衣装 / その他）とキャラクター・場面の紐付けを指定できるようにする。保管の入口が API 側で 4 系統に分かれていることを、UI 上は 1 つのビューに見せる。

**受入基準**

- 取り込み時に役割とキャラクターを指定できる。
- 役割・キャラクターで絞り込める。
- 生成物・登録素材・外部取込・人物参照が 1 つの一覧で探せる。

### R-07 メディアビューアを強化する (#149)

**対応ギャップ** UI リッチ化の現状

一覧でのホバー拡大、全画面表示、ズームとパン、複数枚の比較を共通のビューアとして提供する。既存の A/B 比較とコンタクトシートをこのビューアへ統合する。

**受入基準**

- 一覧のどこからでも同じビューアで拡大できる。
- 拡大表示のままキーボードで前後の候補へ移動できる。

### R-08 ドラッグ＆ドロップを導入する (#150)

**対応ギャップ** UI リッチ化の現状（D&D 無し）

画像をドロップして取り込む。参照枠へドラッグして割り当てる。一覧の並べ替えをドラッグで行う。

**受入基準**

- 画面へ画像をドロップして取り込める。
- 参照画像の枠へドラッグで割り当てられる。
- ドロップ可能な領域が視覚的に分かる。

## Phase 3 ── 工程

### F-06 制作パイプラインを画面に出す (#151)

**対応ギャップ** G-03, G-31

背景 → キャラクター参照 → 音声・BGM → 動画 → 仕上げ、という順序を画面に出す。現在どの工程にいて、何が揃っていて、次に何をするかを常時表示する。API 側にパイプラインの状態機械が無いため、初期はフロント側で工程の定義と進行を保持し、各工程は既存の生成エンドポイントを順に呼ぶ。

**受入基準**

- 場面を選ぶと、必要な工程と現在地が表示される。
- 各工程で「揃っている / 足りない」が分かる。
- 工程を完了して次へ進める。前の工程へ戻れる。
- 前の工程の成果物が、次の工程の入力に自動で入る。

### F-07 作るものを指定して工程を組む (#152)

**対応ギャップ** G-25, UC-B1

場面または作りたい動画を最初に指定し、そこから工程と各工程の Preset 一式を組む。開始前に内容を確認・修正できる。

**受入基準**

- 場面を選ぶ、または日本語で内容を書くことで工程が組まれる。
- 組まれた内容（どの背景、どのキャラクター、どの音声）を開始前に確認・修正できる。
- 開始後は工程ごとに設定を組み直さずに進める。

### F-08 制作進捗を実績から判定する (#153)

**対応ギャップ** G-29, G-30

制作進捗を手動ラベルから、生成実績（採用済み Artifact の有無、工程の完了状態）を根拠にした自動判定へ変える。外部同期 Project でも表示する。手動での上書きは残す。

**受入基準**

- 採用済みの成果物ができると進捗が自動で進む。
- 外部同期 Project でも進捗が表示される。
- 手動でのラベル設定も引き続きできる。

## Phase 4 ── プロンプト

### F-09 プロンプトを差分で編集する (#156)

**対応ギャップ** G-15, G-20

既存の追記マージ（`apps/web/src/prompt/merge.ts` の `mergePrompt`）は追加しかできない。ここに変える・消すを加え、AI の提案を差分として返して差分の単位で採否を選べるようにする。API 応答に差分を加え、差分表示 UI を追加する。JSON textarea の中でプロンプトを編集している 3 箇所を、専用の編集 UI に置き換える。

**受入基準**

- 提案が追加・削除・変更の差分として表示される。
- 既存の記述の変更と削除ができる。
- 差分の一部だけを採用できる。
- 採用しても既存の記述が壊れない。
- JSON を直接編集せずにプロンプトを編集できる。

### F-10 画像を見せてプロンプトを直す (#157)

**対応ギャップ** G-16

生成結果や持ち込んだ画像と、日本語の修正指示をエージェントへ渡し、プロンプトの修正案を差分で得る。`ProposalRequest` に画像を渡せるようにし、provider 側の呼び出しで画像を添付する。provider ごとの対応可否を先に確認する。

**受入基準**

- 画像と日本語の指示から、プロンプトの修正案が差分で返る。
- 「見る → 指示 → 直す → 作り直す」が同じ画面で完結する。
- 画像入力に対応しない provider では、その旨が示される。

### F-11 プロンプト支援を全媒体へ広げる (#158)

**対応ギャップ** G-19

現在 2 箇所（画像の生成・派生）にしかない日本語からの支援を、動画・音声・音楽・合成・スイープへ広げる。

**受入基準**

- 動画・音楽の生成で日本語から条件を組める。
- 媒体ごとに適切な出力（動画ならカメラや動き、音楽なら雰囲気）が返る。

### F-12 ポーズ・衣装・表情の変更を操作語彙にする (#159)

**対応ギャップ** G-13

技術語（i2i / denoise / mask / controlnet）をモードA に残し、モードB には「ポーズを変える」「衣装を変える」「表情を変える」という操作として出す。変換方式と強さは検証済みの値を既定に埋める。

**受入基準**

- 元画像を選び、変えたい要素を選ぶだけで変更できる。
- モードB の画面に denoise / mask / controlnet の語が出ない。
- 元画像との親子関係が記録される。

## Phase 5 ── Preset

### F-13 Preset を 1 つの概念に統合する (#160)

**対応ギャップ** G-22, G-24

Recipe / LookProfile / ProjectTemplate / GenerationDefaults の 4 つを、使用者から見て 1 つの「Preset」として扱えるようにする。内部モデルの統合は別途判断し、まず UI 上で 1 つに見せる。二重の折りたたみの中にある作成導線を表に出す。

**受入基準**

- Preset の一覧・作成・編集・適用が 1 箇所からできる。
- 折りたたみを 2 段開かずに Preset を作れる。

### F-14 生成結果から Preset へ昇格させる (#161)

**対応ギャップ** G-23, G-25

良かった生成物やフォームの現在値から 1 アクションで Preset を作る。Preset に「固定する部分 / 自動で埋まる部分 / モードB で選ばせる部分」を定義できるようにする。

**受入基準**

- 候補ギャラリーから 1 アクションで Preset 化できる。
- Preset 作成時に、モードB で何を選ばせるかを指定できる。
- 選ばせる項目が 2 個を超えるとき警告が出る。

## Phase 6 ── キャラクター

### F-15 キャラクター定義を拡充して独立させる (#154)

**対応ギャップ** G-26, G-27

`ProjectCharacterProfile` に外見・衣装（複数）・声を持たせ、生成 View の入れ子から専用画面へ切り出す。API のスキーマ変更を伴う。

**受入基準**

- キャラクターごとに外見・衣装・声を登録できる。
- 衣装を複数持ち、場面に応じて切り替えられる。
- キャラクター管理が独立した画面にある。
- 定義を直したとき、影響範囲が分かる。

### F-16 参照画像セットを役割枠で管理する (#155)

**対応ギャップ** G-28

動画生成に必要な参照画像を、役割ごとの枠として定義し、キャラクター単位で蓄積・再利用する。novel-writer 側に 7 枚構成（表情 2 種・角度・バストアップ・全身・ポーズ・背景）の検証結果があるため、これを既定の枠とする。

**受入基準**

- キャラクターごとに参照セットの枠が並び、埋まっている枠と空の枠が分かる。
- 空の枠だけを生成して埋められる。
- 別の場面でも同じセットが再利用される。
- 衣装が変わる場合だけ新しいセットを作る。

## Phase 7 ── 資産活用

### F-17 novel-writer のプロンプト資産を参照する (#162)

**対応ギャップ** G-17, G-21

作法・実測知見・既存プロンプトをエージェントが参照できる形で取り込む。正本を書き換えない境界を設計したうえで実装する。タグ型と自然文型の 2 系統をエンジンに応じて扱い分ける。

**受入基準**

- プロンプトの提案が、蓄積された作法と実測知見に沿っている。
- 既存作品でうまくいっている書き方が再現される。
- novel-writer 側のファイルが変更されない。
- エンジンに応じてタグ型・自然文型が選ばれる。

### F-18 タグの実在を生成前に検証する (#163)

**対応ギャップ** G-18

プロンプトに含まれるタグの実在と使用頻度を生成前に確認し、効かないタグを警告する。干渉する組み合わせも検出する。

**受入基準**

- 生成の投入前に、実在しないタグが警告される。
- 重み括弧付きのタグも正しく判定される。
- 品質タグ・rating・絵師タグは検証から除外される。

## Phase 8 ── 仕上げ

### F-19 取り消しを導入する (#164)

**対応ギャップ** G-34

採否の変更・削除・設定の上書きを取り消せるようにする。取り消せない操作は実行前に明示する。

**受入基準**

- 採否の変更と削除を取り消せる。
- 取り消しの導線が通知から辿れる。
- 取り消せない操作は実行前に確認を求める。

### F-20 キーボードで一巡できるようにする (#165)

**対応ギャップ** G-32

生成・採用・不採用・次へ・前の候補をキーボードから実行できるようにする。割り当ての一覧を画面から確認できるようにする。

## 依存関係

```text
Phase 0 (F-01, F-02, R-01, R-02, R-03, R-04)
  ├─> Phase 1 (F-03, R-05, R-06)
  │     ├─> Phase 2 (F-04, F-05, R-07, R-08)
  │     │     ├─> Phase 3 (F-06, F-07, F-08)
  │     │     └─> Phase 6 (F-15, F-16)
  │     ├─> Phase 4 (F-09, F-10, F-11, F-12)
  │     └─> Phase 5 (F-13, F-14)
  ├─> Phase 7 (F-17, F-18)   ※ F-09 の差分表示が前提
  └─> Phase 8 (F-19, F-20, R-09, R-10, F-21)
```

- F-03（モード分離）は Phase 2 以降のほぼすべての前提になる。
- F-04（画像ピッカー共通化）は F-12（ポーズ・衣装変更）と F-16（参照画像セット）の前提。
- F-09（プロンプト差分）は F-10（画像を見せて直す）と F-17（資産の参照）の前提。
- R-01（トークン）は R-02 / R-03 / R-10 の前提。
- F-07（工程を組む）は F-14（Preset 昇格）で定義した「選ばせる部分」に依存する。順序を入れ替える場合、F-07 では暫定の固定 Preset を使う。

## 進め方

- Phase 0 と Phase 1 を終えた時点で、**モードB の画面に見えている操作要素を 15 個以下**にすることを最初の到達点とする。ここまでで「わけが分からない」状態は解消する見込みである。
- Phase 2 と Phase 3 で、作品制作の流れが画面上で成立する。
- Phase 4 以降は、質を上げる改善であり、順序を入れ替えてよい。
- 各フェーズの終わりに、実際に 1 つの場面を通しで作り、想定した手数で回るかを確認する。想定と違えば次のフェーズより先にそこを直す。

## この計画で扱わないこと

- API のデータモデルの大規模な作り替え。UI 改善で必要性が確認できた範囲に限る（F-15 のスキーマ変更が該当）。
- 生成エンジンの追加。5 媒体はすべて実装済みで、不足は確認されていない。
- novel-writer 側への書き込み。参照に限る。
- スマートフォン対応。横長の PC を前提とする。
