# MyComfyUI WebUI ユースケース

## この文書の位置付け

MyComfyUIのWeb UIを「使用者がどう使いたいか」から定義する。現在の実装がどうなっているかは書かない。UIの改善を検討するときの基準として、あるべき使い方を先に固定するための文書である。

[PLAN.md](../PLAN.md)が扱うのは、何を作るか（機能とデータの範囲）である。本文書が扱うのは、それを使用者がどういう順序と頻度で触るか（操作の設計）である。機能としては揃っていても操作の設計が合っていなければ使いにくいUIになるため、両者を分けて書く。

本文書に対する実装のギャップ分析、および改善の優先順位付けは別文書で行う。

## 使用者と前提

使用者は1人だけである。開発者本人が、自分の作品の映像化のために毎日から週数回の頻度で使う。複数人での共同編集、権限管理、引き継ぎは考慮しない。

前提となる作業環境は次のとおり。

- 手元PCのブラウザでWeb UIを開く。生成は LAN 上の Remote GPU PC が行う。
- GPU は 1 台で、重い生成ジョブは直列実行になる。1 ジョブの所要時間は数十秒から数分に及ぶ。
- 素材の正本（Scene、Shot、Canon）は `novel-writer` 側にあり、MyComfyUI からは参照専用である。
- 1 つの作品は数十の Scene と、その下の多数の Shot を持つ。生成物は 1 Shot あたり数十件に達する。

この前提から、UI の設計に次の制約が生まれる。

- **待ち時間が必ず発生する。** 生成を投げてから結果が出るまでの間、使用者は別の作業を進めたい。生成ボタンを押した画面に釘付けにしてはならない。
- **試行回数が多い。** 1 枚の満足いく絵を得るまでに数十回の生成を回す。1 回の生成にかかる操作手数が、そのまま制作速度を決める。
- **生成物は溜まる一方である。** 採用・不採用の判断と、後から目当てのものを見つける手段がなければ、生成物は資産ではなく負債になる。
- **同じことを繰り返す。** うまくいった設定は次の Shot でも使う。再入力を強いる UI は破綻する。

## 2つの利用モード

MyComfyUI の用途は性質の異なる2つに分かれる。**この2つを同じ画面・同じ階層に混ぜないことが、UI 設計上の最重要事項である。**

### モードA ── ラボ（探索）

ComfyUI と AI エージェントを使って、画像・動画・音声・BGM の生成を効率よく試行するための場所。

- **目的** どう作れば良いものが出るかを見つける。
- **使用者の状態** 何が正解か分かっていない。パラメータを触りたい。比較したい。
- **頻度** 新しいキャラクター、衣装、表現に着手するとき。全体の作業時間では少数派だが、密度が高い。
- **UI に求めるもの** 選択肢が全部見えること。細かいパラメータに手が届くこと。条件を振って比較できること。プロンプトを直接編集できること。
- **成果物** 生成物そのものよりも、**「良い結果を出す設定の組み合わせ」** が本体である。これを Preset として残すことがモードAのゴールになる。

### モードB ── 作品制作（Preset 適用）

小説のキャラクターと Scene から、画像・動画・音声・BGM・合成を簡単に作るための場所。

- **目的** 決まった品質のものを、必要な数だけ、速く作る。
- **使用者の状態** 何を作るかは決まっている。作り方は既に確立している。判断したいのは「これで OK か」だけ。
- **頻度** 日常作業の大半。
- **UI に求めるもの** **選択肢が少ないこと。** 次に何をすればよいかが画面から分かること。パラメータを見せないこと。
- **成果物** 採用済みの画・音声・動画・BGM と、その合成結果。

### 現状の問題

現在の UI は、この2つが同じ階層に並んでいる。とくにモードB の領域にモードA の機能が流れ込んでおり、「簡単に作る」はずの場所で選択肢と設定項目が多すぎて、何をどの順に触ればよいか分からなくなっている。

機能が多いこと自体は問題ではない。**モードA に必要な機能が、モードB の画面から見えていることが問題である。**

### 分離の原則

1. **入口を分ける。** 起動直後に使用者はどちらのモードにいるかが明確であり、モードの切り替えは明示的な操作で行う。両モードの機能が同じ画面に同時に並ばない。
2. **モードB には Preset 経由でしか機能が現れない。** モードB の画面に出るのは「キャラクター」「場面」「Preset」「作る」「採否」「次へ」だけである。エンジン名、モデルファイル名、サンプラー、ステップ数、CFG、denoise、ワークフローの構造はモードB の画面に出さない。
3. **モードA の成果は Preset として昇格する。** ラボで見つけた良い設定は、名前を付けて Preset にする。これがモードA からモードB への唯一の正式な経路である。Preset になっていない設定はモードB では使えない。
4. **モードB から抜ける経路は用意する。** モードB で作っていて Preset では足りないと分かったとき、現在の条件を引き継いだままモードA へ移れる。調整して Preset を更新し、モードB へ戻る。
5. **Preset は使用者自身が育てる。** 初期状態で完璧な Preset 群を用意する必要はない。ラボで作って昇格させる流れが回ることの方が重要である。

### 操作頻度の階層

UI 上の場所の割り当ては、機能の重要性ではなく操作の頻度で決める。

**第1階層（モードB の 1 セッション中に何十回も触る）**
現在の工程の実行、結果の採否判断、次の工程・次の Shot への移動、エージェントへの修正指示。

常時画面上にあり、画面遷移なしで到達できなければならない。キーボードだけで一巡できることが望ましい。

**第2階層（1 セッション中に数回触る）**
Preset の切り替え、入力画像の差し替え、場面の切り替え、過去の生成物の検索、モードA への移動。

1 アクションで開き、閉じれば元の作業位置へ戻る。

**第3階層（モードA での作業、および週に数回の保守）**
プロンプトとパラメータの詳細編集、条件振り、Preset の作成と編集、ワークフローの登録、キャラクター定義の管理、モデル選択、整合性チェック。

モードA の画面、または専用画面に置く。モードB の作業中にここが必要になったら、文脈を保ったまま飛べて、戻ってこられる。

**第4階層（初期設定と非常時）**
Remote GPU 接続設定、プロジェクトの新規作成、export/import、backup/restore、外部同期。

奥に置く。実行前に影響範囲を提示する。

## プロンプト資産という前提

モードAの中心はプロンプトである。`novel-writer` 側には既に大量の検証結果が蓄積されており、MyComfyUI はそれを取り込んで活用することを前提に設計する。ゼロから作法を作らない。

既存資産は次の性質を持つ。

- **2つの系統が併存する。** タグ列を並べる系統（Anima 向け。`works/hirohito/Visuals/Prompts/anima/` の Markdown 意図書と YAML Spec、`normal-highschool-life` の character preset）と、自然文で書く系統（`teki-wa-zenin-saikyou` などの Markdown）である。UI はどちらか一方に決め打ちしてはならない。
- **3層構造がある。** 意図（日本語で何を描きたいか）、Spec（モデル・サンプラー・seed を含む完結した生成条件）、展開結果（preset を合成した最終形）の3層である。人間が触るのは意図の層で、生成に渡るのは展開結果の層である。
- **作法が文書化されている。** タグの並び順、品質タグ、絵師タグの扱い、ネガティブの組み方、相互に干渉するタグの組み合わせ、色が出ないときの対処が `anima-prompt` skill にまとまっている。
- **効いた書き方と効かなかった書き方の対応表がある。** 実測に基づく知見であり、プロンプトを直すときの根拠になる。
- **タグの実在を事前確認する手順がある。** 存在しないタグを書いても効かないため、生成前に実在と使用頻度を照会する。
- **衣装・参照注入・動画について検証済みの採用値がある。** img2img の denoise、参照注入の強度、MiniMax H3 の参照画像構成などは既に掃引して結論が出ている。

これを踏まえ、UI は次を満たす。

- プロンプトは**差分で編集できる。** 全体を書き換えるのではなく、タグや文を追加・変更・削除する。既存の記述を壊さない。
- **意図と生成条件を分けて持つ。** 使用者が日本語で書いた意図は残り、そこから展開された実際のプロンプトは別に見える。
- **作法と実測の知見をエージェントが参照する。** プロンプトの提案や修正は、蓄積された知見を根拠にしたものであり、一般論ではない。
- **生成前に検証する。** 実在しないタグ、干渉する組み合わせ、使えないはずの機能の指定は、ジョブを投げる前に示す。

## モードA のユースケース（ラボ）

### UC-A1 プロンプトを作る

**きっかけ** 新しいキャラクター、衣装、場面のプロンプトが必要になった。

**やりたいこと** 日本語で描きたいものを書き、それを実際に効くプロンプトへ落とす。

**理想の流れ**
日本語で意図を書く。エージェントが、蓄積された作法と既存のプロンプト資産を参照して、タグ列または自然文のプロンプトを組み立てる。どちらの系統で出すかは対象のモデルに応じて決まる。

出てきたプロンプトは、そのまま実行する前に検証される。存在しないタグ、干渉する組み合わせ、そのモデルで使えない指定は警告として示される。

**成功条件** 既存の作品でうまくいっている書き方が再現される。使用者がタグの並び順や品質タグの付け方を毎回思い出す必要がない。

### UC-A2 プロンプトを直す

**きっかけ** 生成結果が意図と違う。特定の要素だけ変えたい。

**やりたいこと** 今のプロンプトを保ったまま、必要な箇所だけ足す・変える・消す。

**理想の流れ**
「この部分を変えたい」を日本語で伝えると、変更後のプロンプトが**差分として**提示される。追加されたタグ、削除されたタグ、書き換えられた箇所が色分けで分かる。使用者は差分の単位で採否を選べる。一部だけ採用することもできる。

変更の根拠（なぜそのタグを足したのか、実測でどう効くと分かっているのか）が確認できる。

**成功条件** 直したい 1 箇所のために、プロンプト全体が書き換わらない。修正の履歴が追える。

### UC-A3 画像を見せて直す

**きっかけ** 生成された画像を見て、どこが違うかは分かるが、どのタグを触ればよいかが分からない。

**やりたいこと** 画像と「こう直したい」という日本語を渡して、プロンプトの修正案を得る。

**理想の流れ**
生成結果、あるいは持ち込んだ画像を起点に、日本語で修正指示を書く。「髪がはねすぎ」「もっと引いた構図に」「服が指定と違う」といった書き方でよい。エージェントは画像を見て、現在のプロンプトと突き合わせ、どこを直せばよいかを差分で提示する。

そのまま再生成へ進める。再生成した結果を見てまた直す、という往復が同じ画面で完結する。

**成功条件** 「画像を見る」「指示を書く」「直す」「作り直す」の往復に画面遷移が挟まらない。指示が抽象的でも、蓄積された実測の知見に基づいた具体的な修正が返る。

### UC-A4 当たりを探す

**きっかけ** どう作れば良いものが出るか分かっていない。

**やりたいこと** プロンプトとパラメータを調整しながら生成を繰り返し、方向性を掴む。

**理想の流れ**
プロンプト、モデル、パラメータ、参照画像、ワークフローのすべてに手が届く。生成を投げたらすぐ次の条件を投げられる。結果は過去の試行と並べて表示され、どの候補がどの条件から出たかを即座に確認できる。気に入った候補を起点に「ここから少し変える」が 1 アクションでできる。

**成功条件** 「前の試行とどこを変えたか」を記憶しておく必要がない。良かった条件に戻るのが常に 1 アクションで済む。

### UC-A5 条件を振って比較する

**きっかけ** どのパラメータが効くのか分からない。

**やりたいこと** seed や特定パラメータ、プロンプトの一部を振った生成をまとめて投入し、結果を比較する。

**理想の流れ**
振る軸と値の範囲を指定して一括投入する。投入前にジョブ数と推定所要時間が分かる。実行中は進捗が見え、見込み違いと分かれば残りをまとめて取り消せる。結果は振った軸に沿って並び、どの値がどの結果かが視覚的に追える。

比較して決めた値は、その場で Preset へ反映できる。

**成功条件** 比較結果から得た判断を、手で書き写さずに次へ持ち込める。

### UC-A6 画像を入力にして試す

**きっかけ** 既存の画像を起点にした生成を試したい。

**やりたいこと** 画像を入力に、変換の強さや参照の効かせ方を変えながら試す。

**理想の流れ**
起点にする画像を選び、変換方式（画像からの再生成、参照としての注入、部分的な描き直し）と強さを指定して生成する。方式ごとに検証済みの推奨値が初期値として入っている。元と結果の親子関係が記録され、強さを段階的に振って比較できる。

そのスタックで使えない方式は選択肢に出ない、あるいは理由とともに無効化されている。

**成功条件** 既に検証で結論が出ている値を、毎回探し直さない。使えない方式を試して失敗する時間が発生しない。

### UC-A7 ワークフローを持ち込む

**きっかけ** ComfyUI 側で組んだワークフローを使いたい。

**やりたいこと** ワークフローを登録し、変数として受け取る入力を決め、MyComfyUI から実行できるようにする。

**理想の流れ**
ワークフロー JSON を登録し、どのノードのどの値を変数として外から渡すかを指定する。実行前に、渡される値と実行内容を確認できる。実行時のワークフローはスナップショットとして保存される。

**成功条件** ワークフローを更新しても、過去の生成物が参照する当時のワークフローは失われない。

### UC-A8 キャラクターを定義する

**きっかけ** 新しいキャラクターを扱う。あるいは既存キャラクターの外見設定を直す。

**やりたいこと** そのキャラクターの外見・衣装・声を 1 箇所で定義し、以降の生成すべてに効かせる。

**理想の流れ**
キャラクターごとに、外見のプロンプト、衣装ごとの差し替え、参照画像、声の設定を登録する。衣装は「制服」「私服」「部屋着」のように複数持ち、場面に応じて切り替わる。

定義を直せば以降の生成に反映される。既存の生成物は変わらないが、「定義が変わったので古い」ことが分かる。

**成功条件** キャラクターの外見指定を Shot ごとに書き写す作業が発生しない。定義変更の影響範囲が画面から分かる。

### UC-A9 Preset に昇格させる

**きっかけ** ラボで良い結果を出す条件が固まった。

**やりたいこと** その条件に名前を付けて、モードB から使えるようにする。

**理想の流れ**
良かった生成物、あるいは現在の作業状態から、その場で Preset 化する。Preset を作るときに決めるのは次の3点である。

- **固定する部分** モデル、品質パラメータ、共通プロンプト、ネガティブ、ワークフロー。モードB では触らせない。
- **キャラクター・場面から自動で埋まる部分** 人物の外見、衣装、場所、時間帯、構図の意図。モードB では使用者が選ばない。
- **モードB で使用者に選ばせる部分** あるとしても 1〜2 個に限る。ここを増やすほど、モードB は再び分かりにくくなる。

既存の Preset を更新する場合、既に作った生成物は変わらないが、以降の生成に反映される。

**成功条件** Preset 作成のために別画面で一から入力し直す必要がない。「モードB で何を選ばせるか」が Preset を作る時点で決まる。

### UC-A10 エージェントに任せる

**きっかけ** 案出しや構成の検討を手伝わせたい。

**やりたいこと** 提案を求め、採用するものだけを反映する。

**理想の流れ**
作業中の文脈（場面、キャラクター、現在の条件、直近の生成結果）を渡して提案を求める。提案は差分として提示され、使用者が採否を選ぶ。承認していない生成実行、ファイル操作、外部送信は起きない。何を承認したかは履歴に残る。

**成功条件** 提案の反映が明示的な操作を経たものに限られる。提案内容を手で書き写す作業が発生しない。

## 画像管理

モードBの多くの操作は「既にある画像」を入力にとる。入力になりうる画像は次の3系統であり、**これらが1箇所で等しく選べることが、モードB成立の前提である。**

- **生成物** MyComfyUI で生成した画像。採用・不採用の判断が付いている。
- **プロジェクト登録画像** キャラクターの参照画像、ポーズ参考、背景参考など、あらかじめ登録した素材。
- **アップロード画像** その場で手元から持ち込む画像。

### UC-M1 画像を持ち込む

**きっかけ** 手元にある画像を生成の入力に使いたい。

**やりたいこと** 画像を取り込み、後から探せる状態にする。

**理想の流れ**
アップロードした画像は、どのキャラクター・場面に紐づくか、どういう役割（外見参照、ポーズ参考、背景、衣装参考）かを指定して登録する。同じ画像を二重に持たない。取り込んだ画像はその場で入力として使える。

**成功条件** 取り込みと使用が分断されない。後から役割で絞り込める。

### UC-M2 入力画像を選ぶ

**きっかけ** 画像を入力にする生成を始める。

**やりたいこと** 3系統のどこにあっても、目当ての画像を同じ手順で選ぶ。

**理想の流れ**
入力画像の選択は共通の1つの操作であり、その中で「生成物から」「登録素材から」「アップロードして」を切り替える。選んだ画像はサムネイルで確認でき、複数枚必要な場合は役割ごとに枠が分かれている。

**成功条件** 画像の出自によって操作が変わらない。何枚必要で今何枚選んでいるかが分かる。

### UC-M3 画像を探す

**きっかけ** 以前作ったもの、登録したもののうち、条件に合うものを使いたい。

**やりたいこと** 蓄積した画像から目当てのものを見つける。

**理想の流れ**
キャラクター、衣装、場面、役割、採否、タグ、時期といった軸で絞り込める。サムネイル一覧から目で探せる粒度で表示され、見つけたらそこから生成の入力に直接指定できる。

**成功条件** 探すためにファイルシステムを開く必要がない。見つけた画像がそのまま次の作業の入力になる。

## モードB のユースケース（作品制作）

モードBは単発の生成ではなく、**順序のある工程**である。前の工程の成果物が次の工程の入力になる。

```
作りたい場面・動画を指定
  → Preset 一式が組まれる
  → ① 背景を作る
  → ② キャラクター画像（参照素材）を用意する
  → ③ 音声・BGM を作る
  → ④ 動画を作る
  → 確認・仕上げ
```

各工程では、Preset で生成し、結果を見て、エージェントに日本語で修正を指示し、納得したら確定して次へ進む。**同時に複数の工程を進めない。今どの工程にいて、次に何をするのかが常に画面から分かる。**

### UC-B1 作るものを指定してはじめる

**きっかけ** ある場面を映像にしたい。

**やりたいこと** 何を作りたいかを最初に指定し、そこから先は案内に従って進む。

**理想の流れ**
場面を選ぶ、あるいは作りたい動画の内容を日本語で書く。登場するキャラクター、場所、時間帯、尺といった情報が Canon と既存の定義から埋まる。

そこから、この場面に必要な工程と、各工程で使う Preset 一式が自動で組まれる。使用者はその内容（どういう背景を、どのキャラクターを、どういう音声を作るのか）を確認し、必要なら直してから開始する。

**成功条件** 開始時に決めることが1回で済む。以降の工程ごとに設定を組み直す作業が発生しない。組まれた内容が使用者の意図と違っていたら、開始前に気づいて直せる。

### UC-B2 背景を作る

**きっかけ** 工程①に入った。

**やりたいこと** その場面の背景画像を作る。

**理想の流れ**
場所と時間帯から組まれた Preset で生成する。結果を見て、「もっと夕暮れに」「奥行きを出して」といった日本語の指示で直す。エージェントがプロンプトを修正し、再生成する。納得したら確定して次の工程へ進む。

**成功条件** 背景のためにプロンプトを書く必要がない。直すのは日本語の指示だけで済む。

### UC-B3 キャラクター画像（参照素材）を用意する

**きっかけ** 工程②に入った。

**やりたいこと** 動画生成で参照として使うキャラクターの画像一式を揃える。

**理想の流れ**
動画エンジンが必要とする参照画像の構成（表情、角度、バストアップ、全身、ポーズなど役割の決まった複数枚）が枠として並び、どれが揃っていてどれが足りないかが見える。

キャラクターの定義から Preset が組まれており、足りない枠を順に生成して埋める。既に作ってあるものは再利用され、作り直しにならない。各枚は個別に日本語で直せる。

参照素材はキャラクター単位で蓄積され、別の場面でも使い回される。場面ごとに作り直すのは、衣装や状態が変わる場合だけである。

**成功条件** 必要な枚数と役割が最初から示されている。既に揃っている分を作り直さない。何が足りなくて次へ進めないかが分かる。

### UC-B4 ポーズ・衣装を変える

**きっかけ** 参照素材や既存の画像を元に、ポーズや衣装だけ違うものが必要になった。

**やりたいこと** 元の画像の人物を保ったまま、ポーズや衣装を変えた画像を作る。

**理想の流れ**
元にする画像を選ぶ（生成物・登録素材・アップロードのいずれでもよい）。変えたい対象（ポーズ／表情／衣装）を選び、変更内容を指定する。衣装はキャラクター定義に登録済みのものから選ぶか、日本語で指定する。

変換の方式と強さは、検証済みの値が既定として入っており、モードBでは表示しない。結果を見て日本語で直せる。元画像との親子関係は記録される。

**成功条件** 「どの変換方式を使うか」「強さをいくつにするか」を使用者が考えない。人物の一貫性が崩れない。

### UC-B5 音声・BGM を作る

**きっかけ** 工程③に入った。

**やりたいこと** セリフの音声と、場面の BGM を用意する。

**理想の流れ**
セリフのある Shot が並ぶ。キャラクターに紐づいた声の設定で生成され、使用者は再生して確認する。読み間違いがあれば読みを指定して直す。尺が表示され、動画の尺と合うかが分かる。

BGM は場面の雰囲気から組まれた Preset で生成し、聴いて採否を決める。日本語で「もっと静かに」「テンポを上げて」と直せる。

**成功条件** 音声ファイルを外部のプレイヤーで開く往復が発生しない。読みの誤りが、どこが違うか分かる形で示される。

### UC-B6 動画を作る

**きっかけ** 工程④に入った。前の工程の成果物が揃っている。

**やりたいこと** 背景・参照素材・音声を使って動画を生成する。

**理想の流れ**
前の工程で確定した素材が自動で入力に入っている。動画の内容は場面の記述から組まれた Preset にある。エンジン側の制約（参照画像の枚数、尺、フレームの条件）は実行前に検証され、違反があれば示される。

生成された動画はその場で再生する。「カメラを動かさないで」「もっとゆっくり」といった日本語で直し、再生成する。

**成功条件** 素材を手で選び直す作業が発生しない。制約違反をジョブ投入後に知る形にしない。

### UC-B7 確認して仕上げる

**きっかけ** 工程が一巡した。

**やりたいこと** 画・音声・BGM を合成し、通して確認する。

**理想の流れ**
不足しているものがあれば合成前に示される。揃っていれば合成し、結果を再生して確認する。気になる箇所があれば、その工程へ直接戻って作り直し、再合成する。

**成功条件** 「何が足りなくて仕上げられないか」が分かる。合成結果から問題の工程へ一手で戻れる。

### UC-B8 やり直す

**きっかけ** 出てきたものが気に入らない。

**やりたいこと** もう一度作る。あるいは違う条件で作る。

**理想の流れ**
そのまま作り直せば違う結果が出る（seed を変える操作を意識させない）。日本語の指示で直すのが基本の手段である。それでも合わないときは別の Preset に切り替える。どれでも合わないと判断した時点で、現在の条件を持ったままモードA へ移る導線がある。

**成功条件** 作り直しに毎回同じ入力をやり直さない。Preset で解決しないと判断した瞬間に次の手段へ移れる。

### UC-B9 今日の続きから再開する

**きっかけ** 作業を始めるためにブラウザを開いた。

**やりたいこと** 前回どの場面のどの工程まで進んだかを思い出し、続きに入る。

**理想の流れ**
UI を開くと、進行中の場面と、そのどの工程まで終わっているかが表示される。未完了の工程を選べばそのまま作業に入れる。複数の場面を並行して進めている場合は、それぞれの進捗が一覧で見える。

**成功条件** 開いてから最初の実行までが数十秒で済む。前回の状態を思い出す作業が要らない。

## 両モード共通のユースケース

### UC-C1 生成の進行と詰まりを把握する

**きっかけ** 生成を何本か投げた。結果が返ってこない、あるいは失敗した。

**やりたいこと** 今何が動いていて、あと何本待っていて、失敗の原因は何かを知る。

**理想の流れ**
実行中・待機中のジョブは、どちらのモードにいても見える位置に件数と進捗が出ている。詳細を開けば、どの場面のどの工程かが分かる。

失敗したジョブは、原因が使用者の言葉で示される。設定の誤りなら該当箇所へ飛べる。GPU 側の問題なら接続状態と復旧手段が示される。失敗した条件をそのまま、あるいは修正して再投入できる。

**成功条件** 「返ってこない」状態が、待てばよいのか対処が要るのかを迷わず判別できる。

### UC-C2 過去の生成を再現する

**きっかけ** 過去の生成物と同じものが要る。あるいは Canon が更新されたので作り直したい。

**やりたいこと** 当時の条件で再実行するか、現在の条件で作り直すかを選ぶ。

**理想の流れ**
生成物の詳細から、当時のプロンプト、モデル、seed、パラメータ、参照した Canon のリビジョン、ワークフローが確認できる。再実行は「当時のまま」と「現在の Canon で作り直す」が明確に区別され、どちらを選ぶと何が変わるかが実行前に提示される。当時の条件を再現できない場合は、実行前に理由とともに実行不能と示される。

Canon が更新され、生成時点と現在で内容が異なる生成物には、一覧上に警告が出る。

この情報はモードB の通常作業では表示しない。必要になったときに生成物の詳細から開く。

**成功条件** 再現できるかどうかが、実行してみるまで分からない状態にならない。勝手に現在値で代替した結果を返さない。

### UC-C3 環境を整える・作品を持ち運ぶ

**きっかけ** 初期設定、GPU ホストの変更、別環境への移行、バックアップ。

**やりたいこと** 接続設定やモデルの状態を確認し、プロジェクトを安全に複製・移行する。

**理想の流れ**
Remote GPU への接続状態、利用可能なモデルやワークフローが一覧で確認できる。export/import と backup/restore は、実行前に何が含まれ何が含まれないか、移行先で不足するものは何かが提示される。破壊的な操作は影響範囲を示したうえで確認を求める。

**成功条件** 移行先で開いて初めて不足に気づく状態にならない。

## 横断的に満たすべき性質

**モードが常に分かる。** 今どちらのモードにいるかが画面から明らかで、モードをまたぐ移動は使用者の明示的な操作で起きる。

**次にやることが分かる。** モードB では、現在の工程と残りの工程、今の工程で何が足りないかが常に見えている。

**現在地が常に分かる。** どの Project、場面、キャラクターを扱っているかが、どの画面にいても表示されている。生成の実行対象が意図した対象と一致しているか確認できる。

**日本語で直せる。** 生成結果に対する修正は、パラメータではなく日本語の指示で行えるのが基本である。パラメータの直接編集はモードA の手段とする。

**修正は差分で示す。** エージェントによる変更は、変更前後の差分として提示し、使用者が採否を選ぶ。黙って全体を書き換えない。

**待たせない。** 生成の実行は非同期で、投入後すぐ次の操作に移れる。結果の到着は作業を中断させない形で通知される。

**入力を失わせない。** 書きかけの内容は、画面の切り替えやリロードで消えない。モードをまたいでも保たれる。

**繰り返しを減らす。** 直前の条件、良かった条件、既に作った素材は常に再利用される。同じものを 2 回作らせない。

**取り消せる。** 採否の変更、削除、設定の上書きは元に戻せる。戻せない操作は実行前に明示する。

**失敗を使用者の言葉で説明する。** エラーは技術的なスタックではなく、何が起きて次に何をすればよいかを示す。対処できる設定箇所への導線を持つ。

**キーボードで回せる。** 第1階層の操作（実行、採用、不採用、次へ）はキーボードから実行できる。

**画面を専有しない。** 参照のために開いたものは、作業中の入力を失わずに閉じられる。

## 明確に対象外とすること

- 複数ユーザーの同時利用、権限管理、コメントやレビューのやりとり。
- スマートフォンやタブレットでの操作。画面は横長の PC を前提とする。
- クラウド同期。データは手元と LAN 内に閉じる。
- `novel-writer` 側の正本を MyComfyUI から編集すること。参照に限る。プロンプト資産は取り込んで使うが、正本を書き換えない。
- 汎用的なノードグラフ編集。ComfyUI 本体が担う領域であり、MyComfyUI はワークフローを登録して変数を与える立場をとる。
- モードB を万能にすること。Preset と日本語指示で解決しない要求はモードA で扱う。モードB に設定項目を足して解決しない。
